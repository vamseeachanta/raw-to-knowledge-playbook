## Findings

1. **Vacuous discriminator: `snapshot_evidence` allowance is gated on a singleton, so the stated exclusion has no referent.** Line 169 fixes `metadata_fixture_scope` as *exactly* `firewall_validator_self_check` — the only legal value. Line 196 then says a `metadata_only_fixture` "may also carry `snapshot_evidence` **only when** `fixture_scope=firewall_validator_self_check` and `evidence_mode=shape_only_fixture` … `snapshot_evidence` is invalid on **every other** `metadata_only_fixture`." Because the scope is a singleton, *every* `metadata_only_fixture` satisfies the `fixture_scope` clause — there is no "other" fixture. The real discriminator is `evidence_mode` alone. This is the "shape-only fixture contract contradiction" Claude r6 flagged (line 473) still not cleanly resolved: an implementer reading line 196 could allow `snapshot_evidence` on any fixture. Fix: drop the vacuous `fixture_scope` qualifier and specify the rule as "`snapshot_evidence` on a `metadata_only_fixture` is valid iff `evidence_mode=shape_only_fixture`."

2. **Dual source of truth for the snapshot gate — `#65` already owns `requires_manifest_snapshot_id`, but the plan re-derives it.** The `#65` registry encodes `requires_manifest_snapshot_id: true` for #52-#60 and `false` for #51/#61/#62/#63 (schema lines 189, 252, 259, 266). The plan is scrupulous about *importing* `wave_class` from `#65` (line 190), yet its Request Class Mapping (lines 183-188) and `downstream_snapshot_gate` (line 167) re-derive "which waves need #62 evidence" by hand rather than reading that authoritative boolean. This creates exactly the drift the plan claims to prevent elsewhere: if `#65` later flips a `requires_manifest_snapshot_id`, `#67`'s hardcoded table won't follow. The plan should consume `requires_manifest_snapshot_id` from `#65` as the gate discriminator and add a test asserting agreement (analogous to `test_denied_vocabularies_sync_with_parent_scanner`).

3. **The "passes adversarial plan review" acceptance gate (AC line 408) is unsatisfiable as written — Gemini has returned zero signal for all 6 rounds and the plan defines no quorum or waiver.** The Adversarial Review Summary (lines 460-475) records Gemini `UNAVAILABLE` every round ("unsupported/ineligible-tier authentication error"), and Claude r2 also failed once (line 461). If the review protocol requires three-provider concurrence, the gate can never close; if it does not, the plan must state the quorum rule (e.g., "≥2 providers APPROVE, unavailable providers waived with reason"). As written, AC line 408 has no defined pass condition under a permanently-down provider. This blocks a clean transition to `status:plan-review`.

4. **CI public-scan wiring for `#67` artifacts is under-specified and diverges from the established `#65` pattern — risk of zero public-scan coverage in CI.** The existing `validate.yml` scans a child's public artifacts by passing `--scan-public-path <file>` to the **parent** validator (lines 36-37). The `#67` plan instead relies on its *own* validator calling the parent scanner internally (pseudocode lines 322-326, AC line 429), but Files-to-Change line 347 only says "Run the `#67` validator and unit tests" and never adds `--scan-public-path` entries for `#67`'s contract/classifier/validator/tests/fixtures. If the child-validator-imports-scanner path is not implemented (or the parent module isn't cleanly importable — it's currently exercised as a CLI), `#67`'s public artifacts receive no CI public-scan, silently defeating the plan's core security guarantee. The plan must pin the mechanism (import vs. flag) and, if import-based, add a test that the parent scanner is actually invoked over the full `#67` path list in CI.

5. **(MINOR) AC line 437 `uv run skills/validate_skill.py` omits `python`, inconsistent with every other `uv run python …` acceptance command.** `uv run <script.py>` does resolve, so this is cosmetic, but the inconsistency invites a copy-paste error into the workflow.
