## FINDINGS

1. **The plan's own inline `rg ... --glob` commands collide with its sampling-firewall denial rule — self-scan self-block risk.** Pseudocode (lines 233–237) says reject executable contexts combining denied tools with ACE source tokens, AND allow denied command names "only in fixed methodology headings that do not contain executable prefixes, source paths, pipes, redirects, or command flags." But the plan self-scans "this plan" (line 252) and contains inline code starting with the denied command `rg` that carries flags (`-n`, `--glob`) and a `|` in the regex — see line 307 (in the `text` fence), line 496 (acceptance-criteria inline backticks), and line 44. The parent validator already walks the whole scanned file and emits "unbounded traversal command is not allowed at {path}:{line}" (validator line 612), exempting only `_allowed_denied_traversal_policy_prose`. The plan never states whether the #51 firewall's executable-context denial runs over the whole plan body or only sampling-protocol fixtures, nor whether `rg --glob "*.md"` against `docs skills` (no ACE source token) is exempt. Under the plan's stated allow-rule it is **not** exempt (it has flags and a `|`), so the plan would fail its own gate. Resolve the precedence between the two rules and define the policy-prose exemption explicitly.

2. **The "fixed source-list paths" is never enumerated authoritatively; the plan names two different lists.** Line 282 allows the metadata-evidence shape "only ... for the fixed source-list paths named in this plan," and the positive-fixture acceptance criterion (line 506) and test (line 457) reject "unlisted ACE paths." But the Source-inventory prose (lines 29–32) names only 4 paths (`INDEX.md`, `assets.json`, `_cad-index/index-summary.json`, `llm-wiki`), while the Evidence block (lines 75–81) lists **7** (adds `docs/master-index.jsonl`, `_cad-index/cad-readability-index.tsv`, `.ace-knowledge/index.db`). An implementer hardcoding the 4-path list would make the plan's own 7-row evidence block fail the positive-fixture rule. There is no single canonical enumeration the validator can key off. Add one authoritative fixed-path list.

3. **The token-uniqueness requirement is effectively unfalsifiable by the prescribed fixtures.** Lines 176–180 / 448 require the validator to expand generation-request markers via `generate_public_source_token()` (random `secrets.token_hex(16)`) and assert "duplicates fail validation." Random 128-bit tokens never collide in practice, and good fixtures may not carry concrete `pst_[0-9a-f]{32}` values (line 173), while bad fixtures with concrete tokens are rejected for *being concrete*, not for *being duplicate*. So the duplicate-rejection code path has no fixture that exercises it. Specify how the duplicate-detection branch is tested (e.g., a monkeypatched constant generator), or the "duplicates fail" guarantee is untested.

4. **`test_manifest_snapshot_gate_matrix_covers_all_ingestion_waves` does not catch the escape it names.** Line 460 claims "Future ingestion waves cannot escape #62 gate silently" by asserting the `requires_manifest_snapshot_id=true` set "exactly equals all current ingestion wave rows (#52-#60)." If the only operative definition of "ingestion wave" is the flag itself, a future wave (#64) added with the flag set *false* leaves the true-set unchanged (`{52..60}`), the hardcoded comparison still passes, and the gate is silently skipped — exactly the failure the test claims to prevent. The test only catches a new wave that *already* sets the flag true. Define an independent enumeration of ingestion waves (e.g., cross-reference the full coordination-doc child set and require each non-gate row to be flag-true) so an unclassified new row fails.

5. **Operator-process gates are mixed into the CI Acceptance Criteria list.** The plan correctly carves out a "Pre-Label Evidence Checklist (operator status-transition checks, not CI acceptance criteria)" (lines 525–535), yet Acceptance Criterion line 507 — inside the CI-style Acceptance Criteria section — folds the degraded-quorum / Gemini-auth / reviewer-process narrative back in alongside the testable verdict-parsing assertion. Only the verdict-parsing half is CI-testable (`test_review_artifacts_are_non_empty_and_verdict_bearing`); the quorum half is operator process. Split line 507 so the Acceptance Criteria section contains only mechanically checkable items.

6. **89-hit `sha256` sweep is an unbounded manual-classification burden with no sampling cap.** The plan mandates classifying "every unique `path:line` hit" (lines 307–324, 496) and I confirmed the live count is 89. This is bounded but large, and the plan applies its own "no full-file/large-manifest" discipline elsewhere while imposing a 89-row manual `modify`/`no_change` rationale pass here with no triage cap or batching guidance. Not incorrect, but the effort/precision risk (mis-classifying even one dual-purpose hit flips a public-safety claim) should be acknowledged as a scoped risk rather than an implied one-shot pass.
