## FINDINGS

1. **The single passing fixture is under-specified on two required fields (MINOR).** `required_sampling_fields` (§Proposed Contract Shape, line 182) mandates `manifest_source` and `sort_rule` on every request, and both are constrained to closed enums (`manifest_source` ∈ the six keys, line 181; `sort_rule.term_refs` must each match a #65 private schema term, line 279). But the Fixture Payload Contract for `good-request.json` (line 268) lists only "distinguishing fields" and omits both. The one artifact that must actually pass the validator therefore has unpinned content — two implementers could commit different "valid" `good-request.json` files, and a wrong `manifest_source` value would be a silent gap the plan doesn't guard.

2. **A non-sampling self-check fixture is still forced to name an operational `manifest_source` (MINOR).** `metadata_only_fixture` / `fixture_scope=firewall_validator_self_check` "cannot authorize operational sampling" (line 216) and reads no manifest, yet `manifest_source` is required (line 182) and restricted to the six operational keys. The contract never states which key a self-check should carry or that the field is a formal placeholder in fixture scope. Recommend the contract explicitly exempt or neutralize `manifest_source` (and `sort_rule`) for `fixture_scope`, otherwise the field is semantically meaningless-but-mandatory.

3. **#67 ships zero positive downstream behavior; the issue AC implies an allow-path (MINOR).** Issue #67's acceptance criterion "Manifest-backed downstream waves require #62 snapshot evidence before sampling" (issue body line 26) reads as an allow-when-evidence-present path. The plan authorizes *no* downstream sampling at all in this unit — every ingestion-wave row fails closed with `MISSING_62_EVIDENCE_CONTRACT` regardless of evidence (Request Class Mapping line 211; Deliverable line 166), deferring the first allow-path to #70. This is defensible because #62's evidence contract genuinely does not exist yet, and the plan is transparent about it — but it means #67 delivers only fail-closed downstream semantics. Confirm the user accepts that scope; it is a real narrowing of the issue's literal AC, not a hidden one.

4. **Plan does not reconcile the issue's literal "Blocked by: #51" against its `depends_on_schema_issue=65` (MINOR).** Issue #67 body (line 31) names "#51 core schema slice for wave_class and requires_manifest_snapshot_id fields" as the blocker, but the plan depends on #65. I verified those fields actually live in `artifacts/ace-wave0-ledger-schema.json` (owned by #65), so the plan is *correct* and the issue text is stale — but a closeout check that cross-references the issue's stated blocker will see a mismatch. The plan's Related-issues section explains #51 delegates to #65–#69 (line 34), so this is close to resolved; making the reconciliation explicit against the "Blocked by #51" string would close it.

5. **"Validator forwards each derived manifest path to the parent scanner" leaves subprocess-vs-import unspecified (MINOR/informational).** Pseudocode line 445–446 and Acceptance line 564 say the #67 validator forwards paths to the parent scanner as `--scan-public-path` arguments. The parent is a CLI (`argparse`, verified line 775–799), so a subprocess invocation works, but the plan never states subprocess vs. in-process import — an implementation choice with different failure/exit-code semantics. Low impact given the existing workflow already demonstrates the CLI pattern.
