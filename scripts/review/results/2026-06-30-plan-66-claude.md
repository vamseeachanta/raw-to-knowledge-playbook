## Findings

1. **MAJOR — The fixture contract cannot both "map placeholder fields to #65 private source terms" and pass the parent scanner, as written.** Acceptance criteria (line 218, 241) require `config/ace-public-token-fixture-contract.json` to pass the parent public-surface scan; the pseudocode (lines 137–144) and criteria (line 233) require it to map placeholder fields to the #65 private source terms (`source_id`, `source_sha256`, `private_lookup_key`, `private_lookup_map`, `share_relative_path_private_only`). The parent scanner's `PRIVATE_SOURCE_FIELD_ASSIGNMENT_PATTERNS[0]` (validate_ace_epic_wave_coordination.py:125) flags any line where those terms appear as the left side of a colon/equal assignment. Empirically confirmed: JSON keyed by a private source term **matches and self-blocks**, while list form under a neutral key is safe. The plan's stated mitigation — "parser context, not raw substring allowlisting" (lines 144, 234) — governs the *new* #66 validator's parsing, not the parent regex scanner that the acceptance criteria require the contract to pass. An implementer who naively encodes the placeholder map as a JSON object keyed by private-field name will produce a self-blocking artifact. The plan must explicitly constrain private field names to appear **only as list values, never on the LHS of a `:`/`=` assignment**, in every committed artifact in the scan set (contract, scripts, fixtures).

2. **MAJOR — The opaque fixture-token grammar is never specified, yet the parent scanner already hardcodes the concrete-token shape `pst_[0-9a-f]{32}`.** `PRIVATE_SOURCE_FIELD_ASSIGNMENT_PATTERNS[2]` (validate_ace_epic_wave_coordination.py:127) defines a concrete public token as `public_source_token … pst_[0-9a-f]{32}`. The plan asserts "emitted tokens are opaque … cannot be decoded into source-like parts" (line 134) and tests "hand-authored concrete public token assignments fail" (line 209) without ever pinning the token format. Two unaddressed consequences: (a) if the generator's opaque tokens match `pst_[0-9a-f]{32}`, any committed file containing a token literal (e.g. an expected-output fixture) self-blocks; (b) if they do *not* match that shape, the parent scanner and the new validator disagree on what "concrete token" means, so the bad-fixture rejection test and the public-scan gate test different things. The plan must pin the emitted/forbidden token grammar and reconcile it against the scanner's existing `pst_[0-9a-f]{32}` assumption.

3. **MINOR — Contract ownership claim contradicts the #65 schema.** Pseudocode line 111 asserts the contract validates "owner_issue is #66" and the plan treats #63 as solely the publication-certification owner. But the #65 schema records `downstream_contracts.public_token.owner_issues = [66, 63]` (artifacts/ace-wave0-ledger-schema.json:126–133) — #63 co-owns the public-token contract, not just certification. The import test `test_contract_imports_65_public_token_field` (line 197) will check against an ownership model the schema contradicts; reconcile the singular `#66` owner assertion with the schema's dual `[66, 63]`.
