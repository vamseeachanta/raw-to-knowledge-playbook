Findings:

- [MAJOR] The 5→4 canary class mapping — the core deliverable — is undefined, and `report_workbook` is unreachable from the current classifier. The plan's Gaps section says the existing classes (`data`, `calculation`, `mixed`, `guarded`, `unsupported`) "need an ACE-facing mapping to issue vocabulary (`data_workbook`, `calculation_workbook`, `report_workbook`, `excluded_no_ingest`) without breaking current canary behavior," and `test_existing_canary_classes_map_losslessly` asserts a lossless mapping — but no mapping table appears anywhere in the plan. Verified against `skills/xlsx-input-code-output-canary/resources/xlsx_canary.py` (`classify_inventory`, lines 250–281): chart-only workbooks classify as `unsupported` and chart+formula as `mixed`; no existing class corresponds to `report_workbook`, so producing it requires new classification behavior, contradicting the "without breaking current canary behavior" constraint. The Files to Change row for `skills/xlsx-input-code-output-canary/evals/evals.json` ("Add data/calculation/mixed/report/guarded/unsupported scenarios") silently inserts "report" into what reads as the canary class list. Fix: add an explicit mapping table (e.g., `data→data_workbook`, `calculation→calculation_workbook`, `guarded`/`unsupported`→`excluded_no_ingest`, and a defined disposition for `mixed`), and specify how `report_workbook` is detected — as a new canary rule or as a validator-side overlay — reconciled with the no-behavior-change acceptance criterion.

- [MAJOR] The fixture plan contradicts the plan's own no-committed-workbook-bytes rule. The Artifact Map / Files to Change entry "Create tests/fixtures/ace-wave2-spreadsheet-csv/ — Scan-safe synthetic workbook/CSV/delimited fixtures and negative cases" would commit workbook fixtures under the repo, but the plan's own `test_raw_workbook_bytes_not_repo_local` ("Repo-local workbook bytes → Validator fails") and the canary skill's verification rule in `skills/xlsx-input-code-output-canary/SKILL.md` ("No raw `.xls`, `.xlsx`, `.xlsm`, or `.xlsb` bytes are committed") both forbid exactly that. As written, either the fixture set violates the gate or the test fails on the plan's own fixture directory. Fix: state that workbook fixtures are runtime-generated (the `run_self_test` tempdir pattern in `xlsx_canary.py`) or committed only as inventory JSON; only text fixtures (CSV/delimited) live under `tests/fixtures/ace-wave2-spreadsheet-csv/`.

- [MAJOR] The Deliverable's operational-ingestion condition is unsatisfiable under the cited #67 contract, and the plan doesn't disclose that. The Deliverable says the implementation "will not ingest or publish measured ACE-derived content unless [it] supplies trusted #62 evidence through #70, satisfies #67 caps, and remains on a private/off-public route" — implying a satisfiable path to measured content ingestion exists. Verified against `config/ace-bounded-sampling-firewall-contract.json` and `scripts/ace_bounded_sampling_firewall.py` (line 284): every request class, including `downstream_manifest_backed_sampling`, is forced onto `output_shape=metadata_only_request_record` / `route_target=metadata_only`. Content-byte sampling of workbooks/CSVs is not representable under the current firewall contract, so the extension map's per-format "Expected useful ingestion" percentages and the `% ingested success` pilot have no authorized operational measurement path in this issue. The plan's own pseudocode acknowledges "require #67 metadata-only request shape," making the Deliverable internally inconsistent. Fix: state explicitly that the current #67 contract authorizes metadata-only requests only, scope all measured percentages in this issue to synthetic fixtures, and name a follow-on approved issue as the prerequisite for any content-bytes firewall extension.

- [MINOR] The committed Planned Review and Validation Commands will fail as written if Gemini stays unavailable. The command block passes `--scan-public-path scripts/review/results/2026-07-02-plan-53-gemini-r1.md` (and the header/Artifact Map list the same path unconditionally), but `scripts/ace_public_surface_rules.py` line 84 hard-errors on a missing scan path ("missing public artifact scan path"). Every other 2026-07-02 plan row in `docs/plans/ace-share-ingestion-wave-coordination.md` records "Gemini: unavailable: unsupported-client," and the coordination row for #53 says "Gemini: not-run" — a `gemini-r1` artifact will likely never exist. The plan's only mitigation ("If review produces a later no-MAJOR round, the scan path list will be updated") covers round renumbering, not provider absence, and the Adversarial Review Summary lists Gemini as "PENDING - Not yet reviewed" rather than acknowledging unavailability. Fix: add an explicit unavailable-provider branch — scan only artifacts that exist, and record Gemini as `unavailable: <reason>` in the review summary and the coordination row (the coordination validator's `_review_artifacts_recorded` accepts exactly that form).

- [MINOR] The canary modification is under-scoped relative to the inventory the plan promises. The Pseudocode requires workbook inventory of "charts, date system, external links, macros/protection flags, parser versions," but `xlsx_canary.py` currently records neither external links nor any macro-presence flag (`inventory_workbook`/`observed_flags` cover only structure/sheet protection, charts, tables, names, dates), and the Files to Change reason for `xlsx_canary.py` is only "Emit ACE class mapping/status fields." Likewise, no file change, TDD test, or acceptance criterion covers a legacy `.xls` read path (openpyxl cannot open `.xls`; calamine is used only for sheet names), yet the extension map asserts "60-85% for readable data sheets" for `.xls`. Fix: either widen the `xlsx_canary.py` change scope to include macro/external-link flag emission plus an explicit `.xls` adapter decision with a test, or downgrade `.xls`/`.xlsm` to metadata-only/deferred in the extension map for this issue.

- [MINOR] Vocabulary collision between the proposed workbook class enum and the #65 route-target enum. `excluded_no_ingest` is already a route-target value in the closed set recorded in `docs/plans/README.md` ("`public_llm_wiki`, `private_sidecar`, `metadata_only`, and `excluded_no_ingest`"); the plan reuses the identical token as a workbook *content class*. Since the plan also requires "assign closed route target before any output path is selected," one token now means two different things in the same record, inviting schema drift against `artifacts/ace-wave0-ledger-schema.json` consumers. Fix: name the class distinctly (e.g., `excluded_workbook`) or specify separate `workbook_class` vs `route_target` fields with a validator check that the two enums never intermix.
