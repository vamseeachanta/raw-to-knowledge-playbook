## Findings

### 1. [MINOR] The approval-marker patch leaves a re-implementation loophole: the plan enumerates a 5-check subset of `validate_approval_marker`, not its full contract.
- **Evidence:** Acceptance criterion (plan line 222) requires the split registry to enforce "the same issue URL, exact plan path, 40-character reviewed commit, non-empty review artifact, and verdict-bearing artifact checks as `scripts/validate_ace_epic_wave_coordination.py::validate_approval_marker`." But the parent function (`scripts/validate_ace_epic_wave_coordination.py:432-460`) enforces **more** than those five: all six `REQUIRED_APPROVAL_MARKER_FIELDS` must be present (`Approved by:`, `Approval date:`, `Issue:`, `Plan path:`, `Reviewed commit:`, `Review artifacts:` — lines 169-176, 443-447), and every field except `Review artifacts:` must be **non-empty** (line 446). The plan's prose omits the `Approved by:` / `Approval date:` presence checks and the empty-value checks entirely.
- **Why it matters:** This is exactly the gate codex r1 #3 flagged ("#65 could implement a weaker readiness gate … reopening self-approval or stale-review risk"). The patch is *mostly* there via the "same … checks as `validate_approval_marker`" by-name reference, but an implementer reading the enumerated list could re-derive a marker validator from the prose and ship a strictly weaker gate that admits a marker with a blank approver/date — a self-approval vector.
- **Required fix:** State that the #65 validator must **import and call** the parent `validate_approval_marker` (not re-derive its checks), or enumerate the full contract including the six required fields and the non-empty-field rule, and add a TDD row asserting a marker with an empty `Approved by:`/`Approval date:` is rejected.

### 2. [MINOR] #65 mandates a self-scan over its own public-surface set, which is conceptually #68's deliverable; the boundary is defended in prose but not crisply drawn against re-implementation.
- **Evidence:** Acceptance line 225 / pseudocode lines 153-160 require "The schema validator scans the complete #65 public-surface set." Per `docs/plans/README.md:54` and `docs/plans/ace-share-ingestion-wave-coordination.md:44`, #68's scope is precisely "Public-surface self-scan for control-plane artifacts." The plan carves an exception (lines 32, 47: "only the schema-local public-surface checks needed to keep its own public artifacts safe until #68/#63 generalize the scanner") but acceptance line 225 reads as a standalone self-scan obligation.
- **Why it matters:** Parent/child scope drift is the failure mode the whole #51→#65–#69 split exists to prevent. If the implementer builds a reusable scan engine in `scripts/validate_ace_wave0_schema_contract.py`, #65 partially pre-empts #68 and the two issues will overlap.
- **Required fix:** Add one explicit boundary sentence: #65 only **invokes the existing parent scanner** (`validate_public_artifact_paths`) over an explicit, non-recursive #65 path list and builds **no** new generalized self-scan capability; any reusable scan-engine work routes to #68. Tie acceptance line 225 to "reuse the parent scanner" rather than "the schema validator scans."

### 3. [MINOR] `verification_rejected` is disjoint by exact match but contains the substring `rejected`; the disjointness test could falsely fail (or falsely pass) under substring matching.
- **Evidence:** Plan line 219 claims the enum values are "disjoint from #61 lifecycle states and `page-shape-contract` `parse_status` values." I confirmed exact-match disjointness: #61 lifecycle = `candidate, provisional, verified, rejected, superseded, stale_requires_rescreen` (`docs/plans/README.md:16`); `parse_status` = `verified | provisional-unverified | deferred | rejected` (`docs/03-verification-playbook.md:91`, `skills/page-shape-contract/SKILL.md:37`). None equals any of the four `verification_*`/`validator_passed`/`not_verified`/`independent_review_passed` values. But `verification_rejected` **contains** `rejected`, and `validator_passed`/`independent_review_passed` would substring-match nothing — so a validator that asserts disjointness via `token in value` instead of `value in ENUM` would report a spurious collision on `verification_rejected` ⊃ `rejected`.
- **Why it matters:** The plan's entire purpose is precise, machine-checkable vocabulary; the TDD row (line 193) feeds lifecycle/`parse_status` values as negative samples, and a substring implementation would make that test either flaky or vacuous.
- **Required fix:** One sentence in the pseudocode/TDD section requiring exact set-membership (not substring) comparison for the verification-state enum and its disjointness assertion.
