## Findings

1. **(MINOR — self-scan hazard) The token-generation marker is embedded literally in the plan's own prose (lines 192 and 506), while the plan declares the plan file a self-scan target (lines 289, 381) and rules that the marker "in prose, comments, config files, or public artifacts outside the fixture contract fails validation" (lines 194–196).** Taken literally, when `validate_ace_wave0_control_plane.py` scans "this plan," the definitional occurrences at lines 192/506 are markers in prose and would fail. The plan never states that marker-rejection is scoped to *fixture ledger-row structure* rather than raw substring match. This is the exact "scanned sibling-doc token conflicts / anchor-window self-contradiction" failure class the review history fought in r6–r7. Implementation must (a) detect the marker only inside structured fixture ledger rows, never as a document-wide substring, and (b) add an explicit definitional-occurrence exemption for the spec text, proven by a negative fixture. Not yet testable (validator absent).

2. **(MINOR — overstated guarantee) The "future ingestion wave cannot escape the #62 gate" claim is not mechanically enforceable by #51's own validator as worded.** Pseudocode line 235 and Acceptance criterion line 560 promise the matrix "rejects any ingestion-wave executable binding that omits `wave_class=ingestion_wave`." But the validator can only inspect rows that already exist in the wave map / coordination doc, and the plan states #51 "consumes and scans that parent coordination support but does not modify it" (line 251). A future child issue that is simply never added to the coordination table escapes every #51 check entirely. The guarantee is real only for rows present in the registry; the absolute framing ("any child … fails validation") overstates enforcement. Reword to scope the guarantee to registered rows, or name the registry whose completeness is the actual enforcement point.

3. **(MINOR — terminology drift) Config format is contradictorily described.** Line 212 states both config files are "strict JSON loaded with Python stdlib json; no PyYAML or YAML-only syntax is required," but lines 335 and 338 repeatedly specify rejection of "JSON/YAML objects that assign real private values" and "JSON/YAML key-value pairs." If the configs are strict JSON, the YAML-rejection language is dead/misleading and could push an implementer to add a YAML loader (contradicting line 212). Pick one: either the scanner's generic patterns apply to YAML *surfaces elsewhere* (state that), or drop the YAML phrasing from the config-context rules.

4. **(MINOR — theoretical false-fail) CSPRNG uniqueness assertion can in principle fail a legitimate run.** Lines 206 and 553 require generated `public_source_token` values to be unique across expanded ledger rows with "duplicates fail validation," against a zero-input `secrets.token_hex(16)` generator. A genuine CSPRNG collision (~2⁻¹²⁸) would fail a valid control plane. Negligible in practice, but the duplicate-detection should be specified as a regenerate-on-collision loop rather than a hard fail to avoid a spurious non-deterministic CI failure being indistinguishable from the injected-duplicate test case.
