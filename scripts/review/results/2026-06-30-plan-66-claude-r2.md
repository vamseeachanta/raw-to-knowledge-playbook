`★ Insight ─────────────────────────────────────`
The two existing validators in this repo (`validate_ace_epic_wave_coordination.py:91-127` and `validate_ace_wave0_schema_contract.py:47-57`) deliberately build their forbidden-term constants via **string concatenation** — `"source_" + "id"`, `"proprietary " + "confidential"`, `r"public_" + r"source_token..."`. This is not stylistic: it's how a file that *contains a scanner* avoids tripping its *own* scanner when that file is itself fed through the public-surface scan. Any new self-scanned validator must inherit this idiom or it self-blocks.

## Findings

1. **The plan asserts the new scripts/tests "pass parent scanner" but never specifies the string-concatenation idiom that makes that possible — a naive implementation will self-block.** Acceptance criterion (line 284) and pseudocode (lines 171-176) require `scripts/ace_public_token_fixtures.py`, `scripts/validate_ace_public_token_fixtures.py`, and `tests/test_validate_ace_public_token_fixtures.py` to pass the current parent scanner. But those files must contain the forbidden private-source terms as detection constants. Per `validate_ace_epic_wave_coordination.py:125`, any line where a private source term appears as the left side of a colon/equal assignment is flagged, so a Python constant or dict literal keyed by such a term in the new validator's own source trips the scan. The two existing validators avoid this *only* by splitting every term (`"source_" + "id"`, `validate_ace_wave0_schema_contract.py:47-53`). The plan's "parser context, not raw substring allowlisting" language (pseudocode 156-157) governs how *fixtures* are parsed, not how the *validator source* dodges self-matching. This mechanism is non-obvious and unstated. **Blocker.**

2. **The plan never pins the literal token prefix `pst_`, yet the "agreement with parent scanner" test depends on it.** Acceptance (line 267) and test `test_concrete_token_grammar_matches_parent_scanner` (line 232) require the grammar to match "the current parent scanner's concrete-token assignment class," but the plan only ever says "the existing public token prefix" (lines 138-140, 267). The scanner hard-codes that prefix as `pst_` (`validate_ace_epic_wave_coordination.py:127`: `public_source_token...pst_[0-9a-f]{32}`). An implementer who picks any other prefix produces a validator that silently disagrees with the scanner while the test still passes against its own definition. Pin the literal `pst_` in the contract. **Blocker.**

3. **The "both scanner paths agree" claim is false for the bare-literal and expected-output-row cases.** Acceptance (line 268) forbids concrete token literals "as field assignments **or expected-output rows**," and test line 232 says the assignment "is rejected by **both** scanner paths." But the parent scanner only flags a concrete token in the *assignment* form `public_source_token : pst_<hex>` (`:127`); a bare `pst_<32hex>` in a markdown table cell or a non-`public_source_token` key is **not** caught by the parent scanner. So the new #66 validator is strictly stronger than the parent for those cases — they do not "agree." The test name overstates parity; reword to "the assignment form is rejected by both; bare/row literals are caught by the #66 validator only."

4. **CI-step acceptance commands diverge from the actual workflow invocation style.** Acceptance criteria (lines 286-288) specify `UV_CACHE_DIR=.claude/state/uv-cache uv run python ...`, but `.github/workflows/validate.yml` invokes every validator as plain `uv run python ...` with no `UV_CACHE_DIR`. The plan's "Modify `.github/workflows/validate.yml`" row (line 208) doesn't state which form the new CI step uses, leaving an inconsistency between the documented local command and the existing CI convention. Specify that the workflow step matches the existing `uv run python` style. (Minor.)

5. **Front-matter review-artifact list is inconsistent with the Artifact Map.** Line 10 lists three review artifacts (claude/codex/gemini); the Artifact Map (lines 94-97) lists four, adding `2026-06-30-plan-66-disagreement.md`. Both refer to files that exist, but the two manifests should agree. (Minor.)

6. **Schema cross-link modification is described as safe but the timing is under-specified against `_validate_split_registry`.** Pseudocode (lines 181-186) says to set the #66 `plan_path` and "status snapshot and implementation readiness using the existing approval-marker semantics." Verified safe path: `_validate_split_registry` (`validate_ace_wave0_schema_contract.py:258-259`) short-circuits (`continue`) when `implementation_ready` is falsy, so writing `plan_path` while `implementation_ready:false` passes. The plan's claim is *correct*, but it should state explicitly that the row stays `implementation_ready:false` / `status_snapshot:"plan-required"` until the approval marker exists — otherwise an implementer flipping readiness early triggers the `validate_approval_marker` path (`:265`) and fails the acceptance gate on line 288. (Minor — verified-correct but worth tightening.)

## Blockers
- Finding 1 — the self-scan string-concatenation idiom must be specified, or the new validator/library/test files will fail the parent scanner that the plan's own acceptance criteria require them to pass.
- Finding 2 — the literal token prefix (`pst_`) must be pinned in the contract so the runtime grammar provably matches the parent scanner's hard-coded class.

(Findings 3-6 are MINOR and do not independently block, but 3 should be reworded before the test list is treated as authoritative.)
