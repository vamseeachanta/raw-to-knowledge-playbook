## Findings

1. **Parent-scanner subprocess call is coupled to full parent-coordination state, not just #67 leakage (MINOR).** Plan lines 452–455/542/575 frame the CI step as "invoke the parent scanner … forward each manifest path as `--scan-public-path`" — i.e., a #67-scoped leak scan. But `main()` (`scripts/validate_ace_epic_wave_coordination.py:795–800`) unconditionally also runs `validate_text()` on the coordination ledger **and** `validate_approval_marker(.planning/plan-approved/50.md, PARENT_ISSUE=50, …)`, summing all three error lists before the exit code. So the #67 subprocess returns nonzero whenever the ledger drifts or the **parent (#50)** approval marker is missing/malformed — for reasons wholly unrelated to any #67 artifact leaking. The plan does not acknowledge this false-fail surface. Cleaner: `import validate_public_artifact_paths` directly, or state the coupling explicitly.

2. **`guard_no_source_root_access` return-vs-raise contract is ambiguous for a security boundary (MINOR).** Contract shape (line 202) says the helper "**returns or raises** `ACE_SOURCE_ROOT_ACCESS_FORBIDDEN`", but the acceptance test (line 511) and criterion (line 568) assert it "**Returns** `ACE_SOURCE_ROOT_ACCESS_FORBIDDEN`." For a refusal boundary the distinction is load-bearing: a caller that ignores a returned sentinel silently proceeds, whereas a raised exception halts. "Returns or raises" makes `test_validator_refuses_private_reads_when_ace_share_root_is_set` satisfiable by either control flow, so it can't actually pin the guarantee. Pick one contract.

3. **Review-artifact discovery has no specified, scanner-safe listing API, and the plan forbids itself an escape hatch (MINOR).** The plan requires the #67 validator to *derive* its public-scan manifest by enumerating prefix-matching files under `scripts/review/results/` (lines 446–447, tests at 538–539), yet `test_validator_source_avoids_unbounded_discovery` only says "no *unbounded* traversal APIs." Two of the parent's denied traversal patterns are unconditional recursive Python/path traversal API denials (lines 152–153), with no manifest-path gate, and the plan explicitly bars adding any scanner exemption (line 317). An implementer who reaches for those recursive APIs to discover artifacts self-blocks with no legal remedy. The plan should name the concrete bounded API it intends (non-recursive `Path.glob`/`iterdir` on the single fixed results dir, which are not in the denied set) rather than leave it to implementation.

## Blockers

None. All three findings are MINOR and can be resolved during implementation or in a lightweight patch; none blocks approval of the plan as an approval unit.

`★ Insight ─────────────────────────────────────`
- The plan's sharpest technical claim held up under scrutiny: `MANIFEST_PATH_PATTERN` (line 145) really does *not* contain an `INDEX` token, so the parent scanner would let `cat INDEX.md` through — which is exactly why the plan builds its own per-source cross-product coverage instead of trusting the inherited pattern. That was r9 Codex's finding, and the fix is well-founded, not cargo-culted.
- The recurring architectural tension in this whole wave is **self-blocking**: a public leak-scanner that scans its own source can't contain the very tokens it denies. The plan's "assemble denied tokens from string fragments at runtime" is the load-bearing trick, and the parent's name-scoped exemption (`_allowed_internal_traversal_line`, line 754) shows why — the codebase deliberately refuses to generalize that exemption, forcing every new file to be fragment-clean.
- All three of my findings cluster at the same seam: the boundary between "what the plan asserts the reused parent tool does" and "what `main()` actually does." When a plan reuses an existing entrypoint by subprocess, the reviewer's highest-yield move is reading that entrypoint's `main()` end-to-end — coupling hides in what runs *besides* the function you meant to call.
