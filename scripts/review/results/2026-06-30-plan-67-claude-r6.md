## Findings

1. **Contract internal contradiction — the shape-only fixture cannot legally exist under the stated rules (MAJOR).** Three contract rules conflict: (a) the Request Class Mapping (line 182) binds `target_issue=67` → `request_class=metadata_only_fixture`; (b) the Snapshot Evidence Shape (line 190) states "*For `downstream_manifest_backed_sampling`, the request will carry a `snapshot_evidence` object*" — scoping the evidence object to the downstream class only; yet (c) the `downstream-shape-only-request.json` fixture is a **#67** fixture (`evidence_mode=shape_only_fixture` is "*for #67 metadata-only fixtures*", line 194) that **must carry a complete `snapshot_evidence` object** (TDD `test_downstream_shape_only_fixture_accepts_complete_62_evidence_shape`, line 352). A `target_issue=67` request is forced to `metadata_only_fixture`, which by rule (b) does not carry `snapshot_evidence` — so the fixture the plan commits to shipping is unrepresentable. The plan must state explicitly whether a `metadata_only_fixture` may carry a `snapshot_evidence` object (and if so, amend line 190), or the shape-only fixture will fail its own validator.

2. **Neither committed fixture's `request_class` is specified, so its TDD tests are not authorable from the plan (MAJOR, compounds #1).** Verified by grep: the plan names `good-request.json` and `downstream-shape-only-request.json` only by filename and prose ("Safe metadata-only happy-path", "Safe shape-only #62 evidence fixture") — it never states their `request_class`, `target_issue`, or `target_wave_class`/`fixture_scope` values. Tests `test_bounded_sampling_fields_are_required` and `test_downstream_shape_only_fixture_accepts_complete_62_evidence_shape` (lines 347, 352) load these fixtures and assert pass/fail behavior that depends entirely on those unstated fields. Absent them, the tests cannot be written deterministically and #1's contradiction cannot be resolved.

3. **The "closed" classifier rules for two of six contexts are natural-language heuristics, not machine-checkable (MAJOR).** The plan repeatedly asserts "closed rules" / "parseable and closed" (lines 234, 401, 428), but the Markdown-inline-code rule (line 227) is "*the surrounding sentence introduces it as a command to run, proof command, allowed command, rejected command, or script invocation*" and the fenced-code rule (line 225) keys on fence language being "*shell-like, Python-like, SQL-like, JSON-query-like*". "The surrounding sentence introduces it as a command" requires sentence-level semantic understanding — there is no closed token/grammar rule given for it. This is the same "under-specified classifier rule" the plan says Claude r1 raised and the draft "patches" (line 440); for these two contexts it is not patched. Either provide the closed lexical trigger set (e.g., exact heading anchors + prompt markers, which the plan *does* give for the list-command context) or drop the "closed" claim for inline/fenced prose.

4. **`blocked_pending_62_contract` (accepted) vs. "pending / not-run" evidence (rejected) has no stated discriminator (MINOR).** Line 194 makes `blocked_pending_62_contract` a valid `evidence_mode` that parses; line 202 says the validator "*will still reject placeholder, negated, pending, not-run, missing, forged, or expected-only evidence*." "Blocked pending #62" and "pending" are semantically the same state. The plan should state the discriminator explicitly (presumably: exact match against the closed `evidence_mode`/`reason_code` enum values, with any free-text pending/not-run wording rejected) — otherwise the accept/reject boundary is undefined and the two rules read as contradictory.

5. **`test_validator_refuses_private_reads_when_ace_share_root_is_set` asserts an unobservable negative (MINOR).** Line 357 expects the validator to pass "*without reading sentinel content*." Proving a file was *not* read requires instrumentation (e.g., an unreadable-mode sentinel, an audited open() shim, or a mode-0000 file that would raise if opened) — the plan specifies no such mechanism. As written the test asserts absence-of-behavior with no way to detect a violation, so it can silently pass even if the validator does read the sentinel. Specify the enforcement mechanism.
